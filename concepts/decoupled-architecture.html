Decoupled Architecture

/decoupled-architecture
System design where agent components communicate via typed contracts rather than direct calls, enabling independent deployment and evolution.
Strata: L3, L4 Axes: Orchestration, Execution Status: seed

Explainer

Decoupled Architecture is the practice of separating agent components — planners, executors, memory, tools, evaluators — so that each communicates only through well-defined interface contracts rather than direct function calls or shared mutable state. At L3 (Execution), this means tools and sub-agents expose typed input/output schemas (see Pydantic Contracts). At L4 (Orchestration), this means the orchestrator treats each sub-agent as a black box it can swap without rewiring the pipeline. The key benefit: any component can be upgraded, scaled, or replaced without cascading changes. Common patterns include event buses, message queues, and typed RPC schemas. Anti-pattern: tightly-coupled pipelines where a planner directly imports executor internals, making the system impossible to test or evolve in isolation.

Anti-Patterns

  • Tightly-coupled pipelines where the orchestrator directly imports executor internals make individual components impossible to test, replace, or scale independently.

Mitigations

  • Define typed interface contracts at every component boundary. Use event buses or message queues between planners, executors, and evaluators. Validate contracts automatically with Pydantic or JSON Schema.
